cfg4ai 设计全书
AI 编码工具配置的采集、治理与迁移系统 · 完整设计说明

版本 v0.3（已评审） 日期 2026-08-16 状态：设计冻结候选，P0 待动工 正式名 cfg4ai（2026-08-17 定名）

1这个项目是什么

cfg4ai 是一个面向 AI 编码工具的个人配置管理与迁移系统。它做的事情用一句话说：把你散落在 Claude Code、Codex、VS Code Copilot、Zhanlu（湛卢）、Gemini CLI 等各种 AI 编程工具里的配置——指令文件（CLAUDE.md / AGENTS.md）、MCP 服务器、skills、agents、commands、hooks、权限设置——统一采集到一个"单一事实源"仓库里管起来，然后可以在任何时刻、把这些配置字段级保真地交付给任何一个已接入的工具——主流或非主流（如 mobile coder）都行；尚未接入的新工具，补一个适配器即可纳入交付范围。

它解决三类日常痛点：

  • 换工具：今天用 Claude Code，明天团队要求用 Codex——你在 CLAUDE.md 里沉淀了半年的编码规范，难道手工抄一遍再逐句改格式？
  • 换机器 / 重装系统：Windows 工作站、家里的 macOS、公司的麒麟 Linux 服务器，三处配置如何一致？
  • 配置治理：全局配置和项目配置混在一起，删了什么东西没人记得，MCP 服务器里的 API key 明文躺在各个目录——你甚至不确定自己到底有哪些配置。

用 30 秒理解它的工作方式：

# 1. 看看本机有哪些 AI 工具配置
cfg4ai scan

# 2. 全部采集进统一仓库（自动识别敏感信息并抽取到系统钥匙串）
cfg4ai collect

# 3. 把配置交付给另一个工具（先预览，确认后落盘）
cfg4ai export --to codex --dry-run
cfg4ai export --to codex

# 或者一步到位
cfg4ai migrate --from claude-code --to zhanlu --ai

本文档是这个项目的完整设计说明。它由四份技术规格文档（总体架构、IR 数据模型、CLI 规范、适配器规范）、一轮五维专家评审、一轮覆盖 20 个工具的生态调研与红队对抗审计合并而成，适合从头通读。如果你只想快速了解设计要点，读第 3、4、5 章即可。

2问题：AI 配置的碎片化困境

2025 年以来，AI 编码工具从"插件"演化为"平台"，每个工具都发展出了自己的一套配置生态。问题是：每家都是私有格式，互不通用。

这还只是五个工具。我们在生态调研中系统核查了 20 个工具（见第 12 章），每个都有自己的概念模型：Cursor 有四种规则激活模式和团队强制规则，Roo Code 有 custom modes（人格+工具权限+文件白名单的复合体），Goose 有 recipes（带参数和重试的工作流编排），Windsurf 有 AI 自动生成的 memories……碎片化的程度远超"换个文件名"这么简单。

碎片化的代价具体而微：

  • 迁移靠手工复制粘贴 + 凭感觉改写，丢三落四是常态；
  • 配置没有版本管理，改坏了回不去；
  • API key 等敏感信息以明文散落于各处 env 字段；
  • 项目目录一搬家，"这个项目该用哪套配置"就断了线索；
  • 换操作系统（尤其是国产麒麟 Linux）时，连"配置文件在哪"都要重新考古。
设计输入这些痛点直接决定了项目的四个功能目标：G1 统一采集治理、G2 全局/项目双层模型、G3 项目关联与重定位、G4 跨工具迁移交付；以及一个平台目标 G5：Windows / macOS / Linux（含麒麟）全平台可用。

3设计哲学：四条第一性原理

在展开所有设计细节之前，先交代这个项目做决策的"公理层"。后面每一章的具体机制，都可以回溯到这四条原理——它们也是本项目接受或拒绝一个设计方案的判据。

原理一：信息守恒是迁移唯一可证明的正确性标准

两个工具的能力集不同（Claude Code 早有 subagent，VS Code Copilot 的 agents 体系则成熟得晚得多），数学上不存在任意两者之间的无损双射。所以"零丢失"的承诺不能建立在"完美映射"上，只能建立在"原始数据永远可达"上。由此导出系统的骨架分工：原始文件的快照（blobs）是事实层，IR 只是其上的索引与视图。任何 IR 表达不了的内容，blob 兜底。这是对抗模型不完备的保险丝。

原理二：IR 的表达力上限 = 调研的完备性

统一数据模型（IR）的标准字段，本质上是各工具配置 schema 的"交集的泛化"；私有扩展位（x-<tool>）是"差集的容器"。调研漏一个维度，模型就漏一个维度，数据就在这个维度上静默丢失——而且最危险的是，这种丢失连测试都发现不了（因为测试也是基于同样的不完备认知写的）。这就是为什么本项目在动工前先做了一轮深调研：对 5 个适配目标做了约 850 个字段的逐字段清点，另对 15 个扩展工具做了调研卡片式的压力测试（第 13 章），而不是边写边补。

原理三：导出的本质是投影，投影的正确性由能力矩阵决定

导出到某个工具，就是把统一模型"投影"到该工具能力所支撑的子空间；投影不下的部分，以最低损耗的形式携带过去（比如降级为目标文件里的一段附录注释，而不是直接扔掉）。每个适配器必须如实声明自己的能力矩阵（支持/部分支持/不支持），投影的规则才有据可依。

原理四：正确性无法正向证明，只能靠证伪机制逼近

永远无法证明"所有迁移都正确"，只能建立"出错必被发现"的机制。因此系统内建了层层证伪手段：导出后重新导入做语义对比（round-trip 自检）、golden-file 测试、38 条对抗用例回归、真实世界样本回归。发现不了问题 ≠ 没有问题——这条谦逊原理贯穿了从写入协议到安全设计的所有章节。

4总体架构：Hub-and-Spoke

最朴素的做法是给每两个工具之间写一个转换器。但 N 个工具需要 N×(N-1) 个转换器，且每新增一个工具都要改写所有已有转换器——这条路在组合上就是死路。

cfg4ai 采用编译器领域的经典解法（LLVM 同款思路）：定义一套统一中间表示（IR, Intermediate Representation）作为枢纽（hub），每个工具只需实现一对"导入器/导出器"（spoke）。N 个工具只需要 2N 个适配器，新增工具 = 新增一个适配器，与存量零耦合。

Claude Code ──┐ Codex CLI ───┤ Importer → 【 IR / SSOT 仓库 】 → Exporter ├──→ Claude Code Copilot ───┤ ├──→ Codex Zhanlu ───┘ └──→ 任意新工具

图 4-1 · Hub-and-Spoke 架构：复杂度从 O(N²) 降到 O(N)

让这个架构真正成立的，是两个支撑机制：

4.1 扩展命名空间 x-<tool>：保证往返无损

每个工具都有自己特有的字段（Claude 的 hooks 细节、Codex 的 sandbox 策略）。导入时，这些无法映射到 IR 标准字段的内容被原样收进 x-claude-code、x-codex 这样的扩展位；之后无论配置被迁移到多少其他工具，这些扩展位都只读透传；一旦导出回原来的工具，它们被原样还原。其生命周期规则只有三句话：

  • x-<tool> 绑定"最近一次源自该工具的导入"；
  • 异构工具再采集，只更新标准字段和自己的扩展位，绝不碰别家的；
  • 导出回某工具时，标准字段以最新值为准，扩展位只负责补回该工具特有的字段。

这三条规则使得"A→B→C 再多跳跳回 A"的多跳迁移也有明确的保真语义。

4.2 来源追踪 origin：每个条目都知道自己从哪来

每个 IR 条目都携带来源信息：来自哪个工具、哪个文件（以 ~/ 或 %APPDATA% 变量形态记录，保证跨机器可移植）、什么时候采集的、原始内容 hash 是多少。这支撑了三个能力：增量采集（hash 没变就跳过）、差异审计（SSOT 与磁盘现状对比）、以及第 6 章提到的回写路由（老条目写回原文件）。

5统一中间表示 IR

IR 是整个系统的心脏。它以 YAML + Markdown 的形态存储，设计目标是四个词：可校验、可合并、可往返、Git 友好。

5.1 五层配置模型

先澄清一个口径：第 2 章目标 G2 说的"全局/项目双层"，是物化语义的主干（导出时就是全局与项目两层合并）；但在采集侧，真实世界的层级远不止两层。初版设计只有"全局/项目"两层，生态调研立刻击穿了这个假设：Claude Code 有 settings.local.json（项目内的私人层，不入 git），Cursor 有团队下发的强制规则，OpenCode 支持 MDM 企业托管层，Gemini 的 settings 事实上有四层。于是 v0.3 把配置层级扩展为五层：

层级优先级含义真实例子系统行为
managed最高企业/组织下发Claude managed settings、OpenCode MDM、Windsurf System 层只读采集，供审计比对，不参与导出物化（管理权在企业侧）
remote高组织远程订阅Cursor 团队规则、OpenCode remote 配置源采集并可参与合并
local中项目内私人层.claude/settings.local.json、CLAUDE.local.md参与合并；不同步（私人内容不上远端）
project低项目级<proj>/CLAUDE.md、.mcp.json参与合并
global最低用户级~/.claude/CLAUDE.md、~/.codex/config.toml参与合并，作为基底

5.2 八类实体

对 5 个适配目标的约 850 个配置字段逐字段清点、并用 15 个扩展工具的独特概念逐一压力测试之后，它们最终被归纳为八类实体。这个归纳不是拍脑袋——每一类都有明确的现实对应物，每一个标准字段都能说出"它在哪几个工具里存在"：

其中 Hook 成为一等实体是调研的直接产物：Claude 的 31 个 hook 事件、Codex 的 11 个、JetBrains Junie 的 7 个在语义上高度重叠（都有会话开始、工具调用前后、通知、停止等），标准化条件成熟；各家的交集事件名构成标准枚举，各家特有事件进扩展位。

另一个值得一提的归纳是激活方式 activation。Cursor 的规则有四种激活模式（始终生效/模型判断/按文件 glob/手动 @），Windsurf 有 trigger 四态，JetBrains 有五态，Zhanlu 的 skill 靠 description 语义路由——这些看似各异的概念，公共面是同一个枚举：always | model-decision | glob | manual | scene。这就是"交集泛化为标准字段"的典型一例。

5.3 合并语义：继承与覆盖的精确规则

"项目配置继承全局配置"说起来一句话，真正的魔鬼在细节里。系统定义了三种合并策略，每种都有精确语义：

  • merge-by-id（浅字段级合并）：同一个 id 的条目，项目层出现的字段覆盖全局同名字段，数组字段整体替换（不逐项合并），项目层没写的字段继承全局。举例：全局定义了 MCP server 的 8 个字段，项目层只想调整环境变量——只需重写 env 这一个字段（该字段作为整体覆盖全局值），其余 7 个未写字段自动继承全局。
  • concat（层级序拼接）：用于指令类。先按层级分层（全局在前、项目在后——因为后出现的指令语境上更"近"），层内按优先级数值排序，同值再按来源路径字典序。多条指令物化回单个文件时，用 <!-- cfg4ai:begin <id> --> 边界注释分隔，下次采集还能还原成独立条目。
  • entry-replace：单值场景的整条替换。

还有一条重要原则：IR 的合并语义是唯一权威，不随目标工具改变。现实世界里各工具的合并行为并不一致——Claude 的 settings 数组是跨层级拼接去重的，Codex 用正极性的 enabled（IR 用 disabled），Cline 的 skills 是全局优先于项目（与直觉相反）。这些差异全部登记在适配器规范的"目标语义差异表"里，由各适配器在导入/导出的双向转换中自行消化，IR 层保持干净。

5.4 删除传播与墓碑：红队逼出来的设计

初版设计里，增量采集靠内容 hash 检测"变更"。红队审计指出了一个致命盲区：hash 能发现变化，发现不了消失——而且更可怕的是"假消失"。设想：你的移动硬盘掉线了，上面的项目配置目录暂时不可读。采集程序发现"上次采集的条目这次全都不见了"，如果把它当作"用户全删了"处理，打上删除标记，下次导出就会把这些"已删除"的配置从所有工具里清掉——一次盘掉线演变成配置清空事故。

v0.3 的完整删除语义由此定为四条规则：

  1. 防误判：源目录不存在/不可读 → 中止该位置采集并告警，绝不标记删除；只有目录健在而条目消失，才标记墓碑（tombstone）。
  2. 遮蔽规则：项目层删除了某个全局也有的条目时，项目层墓碑要遮蔽全局同 id 条目——否则"已删除"的配置会从全局层"复活"。
  3. 边界限定：墓碑 reconcile 只作用于本次实际采集的位置集合，多个 clone 共存同一 profile 时互不踩踏。
  4. 空集保护：合并后的有效配置如果一条都不剩，而目标工具里明明还有文件——拒绝导出，必须 --force 加显式警告（--yes 也不豁免此项）。

5.5 保真承诺的边界（诚实清单）

与其含糊承诺"零丢失"，不如把承诺分级写清楚：

  • 强承诺：字段级零丢失。所有语义字段经扩展位往返一致。
  • 显式免责：文档层不保证。JSONC/TOML 的注释、键的顺序、排版格式，经 YAML 中转后不保证保留。
  • 可选兜底：对注释密度高的源文件，可以把原文整体存快照（raw_blob），导出时选择"以原文为底做字段级补丁"（overlay 模式）而非全量重渲染。

6迁移引擎

6.1 六步管线

一次导出（export）在引擎内部的完整旅程：

Load 加载 profile（全局 + 项目） ↓ Merge 五层合并（含墓碑遮蔽）→ 得到有效配置 ↓ Map IR 映射为目标工具模型（规则引擎，确定性） ↓ Assist （可选）AI 语义转换——引擎层主导，适配器不感知 ↓ Render 渲染为目标格式（YAML/JSON/TOML/Markdown） ↓ Verify 两级校验：格式校验（必做）+ round-trip 自检（尽力） ↓ Write 写入协议落盘（见 6.3）

其中 Verify 的 round-trip 自检值得单独解释：导出完成后，引擎会拿着写入清单（Export 返回的 []WrittenFile）把刚写的文件再导入一遍，与导出前的模型做语义对比。差异（扣除白名单内的已知降级项）会逐条列给用户。这是"原理四"的直接体现——不假设转换是对的，而是每次转换后都尝试证伪它。

6.2 规则优先，AI 兜底

系统里有两类转换，分界刻意划得很清楚：

转换类型方式例子
确定性字段映射规则引擎（代码）mcpServers → servers 键名转换
格式重组模板渲染skills/*.md → .github/prompts/*.prompt.md
语义改写AI 接口把 Claude skill 描述润色成 Copilot prompt 风格
冲突合并建议AI 接口目标已有同 id 条目时给出合并建议
语言适配AI 接口中文指令 ↔ 英文指令（目标工具对英文更友好时）

围绕 AI 的三条铁律：

  1. 职责归属引擎层。适配器只做格式双向转换，完全不接触 AI——这样适配器可以脱离 AI 独立做 golden-file 测试，AI 也不会成为格式正确性的变量。
  2. 结果必须经人确认。AI 转换永远先以 dry-run 形式预览差异；--yes（CI 模式）也不豁免这项确认，无人值守场景必须显式加 --ai-approve，且会留下决策日志。
  3. 出域必须知情同意（consent）。首次使用 AI 功能时显式告知端点和发送内容类别；AI 配置（端点/模型）一旦被改动——包括被 git 同步下来的改动——下次使用前强制重新确认（这条是红队"端点投毒"用例的直接修复）。另外，没有配置 AI 时系统完全可用，语义转换退化为"原样搬运 + 警告"。

6.3 写入协议：把文件写对是门手艺

配置工具最败人品的行为就是把用户文件写坏。写入协议用一组硬性规则把这件事管住：

  • 单文件原子：先写临时文件（必须和目标同卷同目录——跨盘 rename 在 Linux 直接报错、Windows 直接失败），写完 fsync，再 rename 覆盖，最后 sync 父目录。
  • 批量不承诺原子，承诺可回滚：一批文件先把临时文件全部就位，再逐一 rename；中途失败则逆序清理 + 自动恢复快照。措辞从"不留半成品"修正为"单文件原子，批量以快照补偿"——这是对原子性承诺的诚实降级。
  • Windows 占用重试：杀毒软件、搜索索引、正在运行的 IDE 都可能瞬时锁定目标文件，rename 遇到共享冲突时指数退避重试，终失败则明确报出"哪个文件被谁占用"。
  • 符号链接穿透：很多用户把 ~/.claude 软链到 dotfiles 仓库。写入前必须解析到真实路径再写——否则原子替换会把链接本身换成普通文件，静默破坏用户布局。
  • 外来内容识别：系统持久化一份"导出清单"（哪个文件、什么时候、内容 hash 是什么）。下次导出前比对：文件不在清单里＝外来内容，要确认；在清单但 hash 变了＝被外部改过，要确认；一致＝本工具产物，直接覆盖。确认选项固定为四种：覆盖 / 跳过 / 看差异 / 备份后覆盖。比对前先做字节级规范化（换行符、BOM），防止 IDE 自重写格式造成"确认疲劳"。
  • 热重载提醒：探测到目标 IDE 正在运行时，导出会提示"部分设置需重启或 Reload Window 生效"。

7项目关联与指纹

项目配置只有知道"自己属于哪个目录"才有意义。系统在注册表（registry.yaml）里维护"项目 ID ↔ 磁盘路径 ↔ 配置档案"的绑定，并解决两个棘手问题：

7.1 项目搬家了怎么办——指纹重定位

目录从 D:\proj 迁到 F:\proj 后，在新位置执行 cfg4ai relink，系统凭项目指纹重新认亲。指纹按优先级取：规范化后的 git remote 地址（统一剥掉协议差异、尾部 .git、host 小写、scp 风格转标准形式——否则 git@github.com:u/r.git 和 https://github.com/u/r 会被当成两个项目）＞ 根目录名+首次提交 hash ＞ 根目录名。

7.2 防张冠李戴——两道判别

红队构造了两个"身份劫持"场景，v0.3 均已封堵：

  • 同名不同源：同一个 remote 在公司和家里各 clone 了一份，它们不是同一个"项目实例"。规则：指纹命中后还要首次提交 hash 一致并经用户确认才合并；否则新建项目 ID，只记录 same_remote_as 亲缘关系。
  • 路径复用：目录改名后，原地新建了一个同名的不同项目。旧规则下采集会"路径命中即采"，把新项目的内容写进旧项目的档案。规则：即使路径直接命中注册项，采集时仍复核指纹，不匹配就警告并建议 relink。

8存储：SSOT 仓库

所有知识都存在一个纯文本、Git 友好的仓库里，默认位置遵循各平台规范（$XDG_CONFIG_HOME/cfg4ai、%APPDATA%\cfg4ai、~/Library/Application Support/cfg4ai）：

$CFG4AI_HOME/ ├── config.yaml # 自身配置：AI provider、secret 后端、合并策略 ├── registry.yaml # 项目注册表 ├── profiles/ │ ├── global/ # 全局档案（与项目档案结构同构）：manifest + instructions/ + mcp.yaml + │ └── projects/<pid>/ # skills/ + agents/ + commands/ + workflows/ + hooks.yaml + settings.yaml ├── exports/ # 导出清单（外来内容识别的依据，随库同步） ├── snapshots/ # 快照：manifest + blob 引用（天然去重） ├── blobs/ # 脱敏后的原始内容寻址存储（不入库） ├── secrets.age # 可选：加密文件 secret 后端（0600，强制 gitignore） ├── cache/ logs/ # 不入库 └── .lock # 仓库级写锁

三个设计决定值得说明：

  • 不用数据库。索引直接走文件系统，保持 KISS——整个仓库 git init 推到私有远端就是跨机同步。
  • 并发有锁。写操作全程持跨平台文件锁（两个终端同时跑 collect、sync 与本地写入竞争，都被串行化）；锁持有者异常死亡由 doctor 检测清理。
  • 权限收紧。仓库目录 0700、文件 0600，每次写后校验（多用户 Linux/麒麟服务器上，默认 umask 会让你的私有编码规范全员可读）；检测到仓库被放在 OneDrive 等云同步目录会强警告（既有泄露风险，云盘的文件锁还会击穿原子写入）。
  • 大体积内容与配置分开放。Windows 上配置与元数据放 %APPDATA%（Roaming），快照/blobs/缓存等大体积内容落 %LOCALAPPDATA%——避免大文件随域漫游同步。

9跨平台支持

目标平台六个构建目标：windows/amd64、darwin/amd64、darwin/arm64、linux/amd64、linux/arm64、linux/loong64（龙芯，标注未实测）。麒麟 Kylin 按 Linux 处理——但"能编译"和"能跑好"之间隔着一整套工程纪律：

9.1 麒麟适配的关键：静态编译纪律

银河麒麟 V10 服务器版是 openEuler 血统（glibc 2.28、内核 4.19），桌面版是 UKUI/deb 生态，两系系统库差异真实存在。Go 的 CGO_ENABLED=0 纯静态编译产物只依赖内核系统调用 ABI，可以把 glibc 版本、包生态分裂全部免疫——一套 linux 二进制通吃 Ubuntu/CentOS/openEuler/Kylin。但这个红利是易失的：任何一个引入 CGO 的依赖都会把 glibc 地板抬回来。因此纪律写死：发布构建强制 CGO_ENABLED=0，CI 对全部目标断言产物确为静态（ldd 检查），并在麒麟 V10 服务器（headless）+ UKUI 桌面两类环境跑冒烟矩阵。

10安全设计

安全设计围绕一个核心承诺展开：secret 明文永不进入仓库、永不上远端。红队审计把这条承诺逼出了三个真实漏洞，修复后形成了现在的纵深防御。

10.1 Secret 三级后端降级链

敏感值（API key、token）采集时即被抽取，仓库里只留下 secretref://cfg4ai/<profile>/<entity-id>/<field> 占位符。值本体按降级链存储：

  1. 系统钥匙串（首选）：Windows Credential Manager / macOS Keychain / Linux Secret Service，经 99designs/keyring 统一抽象；
  2. 加密文件（age 加密，0600 权限）：这是 headless 环境的唯一出路——Linux 钥匙串依赖桌面会话的 D-Bus 服务，麒麟服务器版、容器、SSH 会话、CI runner 上必然缺席；
  3. none：显式声明不存，导出物留占位符由人手工填写。

10.2 红队发现的三个漏洞与修复

漏洞一blob 保真与脱敏自相矛盾。初版设计里 blobs 保真存储原始文件、且 sync 是全目录 git 同步、无任何排除规则——而 ~/.claude.json 的 env 里明文 API key 是常态，两条叠加等于明文具化出域。修复是双管齐下：blob 只存脱敏后内容（双 hash 分工：原始 hash 用于增量比对、脱敏 hash 指向 blob；落盘管线强制"先扫描替换、后落盘、零命中校验才提交"）；同时 sync 改为白名单制，blobs、snapshots、logs 等一律排除在同步之外（这正是第 8 章目录树标注"不入库"的由来）。
漏洞二自由文本里的 secret 经同步上远端。用户在 CLAUDE.md 正文里贴了真实 key（教学示例里贴假 key 更是常见），扫描若改写正文会破坏内容，只警告又会随 sync push 上远端。修复：处置分级——结构化字段（env/headers/args）命中默认抽取（可否决），自由文本命中只警告不改写；同时 sync push 前增加全仓预检扫描，命中即阻断或显式确认，CI 不得对 sync 放行"部分成功"退出码。
漏洞三AI 端点投毒。config.yaml 在同步白名单内，恶意远端可经 pull 把 AI 端点改成攻击者地址，下次 --ai 你的私有编码规范就流向了第三方。修复：AI 配置段变更后强制重新 consent；日志默认只记元数据（不记 prompt 原文）；企业场景支持端点白名单。

10.3 敏感扫描

扫描规则库外置（对齐 gitleaks 规则集 + 高熵串检测），支持用户自定义规则和豁免清单。覆盖 sk-*、ghp_、glpat-、xoxb-、AIza、hf_、JWT（eyJ 前缀）、PEM 私钥头等模式。

12.1 适配器接口

每个适配器实现四个方法（Go 接口，全部带 context.Context）：

type Adapter interface {
    Meta() ToolMeta                                    // 标识、版本护栏、能力矩阵
    Detect(ctx) ([]Location, error)                    // 只读探测（含进程运行检测）
    Import(ctx, loc) (*ir.Bundle, error)               // 工具格式 → IR
    Export(ctx, bundle, opts) ([]WrittenFile, error)   // IR → 工具格式（返回写入清单供自检）
}

配套规范十条，核心几条：Detect 不许写任何文件；表达不了的内容进扩展位绝不静默丢弃；写文件必须走统一的 atomicfile 通道；每个适配器声明新增条目的默认写入位置，对 ~/.claude.json 这类"混杂运行时状态的文件"只许局部补丁、禁止整体重写；目标工具的合并语义差异登记到公共差异表。能力矩阵用三档（支持/部分支持/不支持+备注）表达，导出降级由此驱动。降级遵循两级规则：目标工具有最近概念就映射为该形态（如 Copilot 的 prompt 文件），没有则并入指令附录并保留元数据；降级结果逐条警告、可回滚。

14技术选型：为什么是 Go

语言选型经过专项对比分析（完整报告：docs/review/GO-VS-RUST.md），最终于 2026-08-16 拍板 Go。决策依据按重要性排序：

14.1 决定性因素一：YAML 保注释 round-trip 的生态落差

本项目的配置仓库是人工可编辑的 YAML 文件，导出时丢注释等于破坏用户手工维护的内容——这直接挂钩"字段级零丢失"的核心承诺。Go 侧 yaml.v3 的 Node API 保留注释/键序/样式，经过 Kubernetes 规模验证；Rust 侧 serde_yaml 已于 2024 年 3 月归档，替代 fork 均无注释保留能力。选 Rust 意味着要么放弃核心承诺，要么自研注释保留层。这一条单独即可定调。

14.2 决定性因素二：六目标 + 麒麟的分发工程成本

Go：GOOS/GOARCH 一把梭，goreleaser 一份配置出全部静态二进制；CGO_ENABLED=0 天然免疫麒麟的老 glibc。Rust：交叉链接器要 zigbuild/cross/cargo-xwin 组合，macOS 目标仍需 Apple SDK，麒麟要切 musl target 并回归全依赖树。都有解法，但对个人/小团队是持续的 CI 维护税。

14.3 决定性因素三与四

  • git 依赖的 C 形态：go-git 纯 Go 对交叉编译零影响；Rust 要么背 libgit2 的 C 依赖，要么押注 API 未稳的 gix 0.x。
  • 所有权模型对本项目是 overhead：主体工作是"读 YAML/MD → 树变换 → 写出"的胶水逻辑，Rust 的借用规则在此产生真实摩擦，而其并发/内存安全收益在单线程、短生命周期、纯 IO 的 CLI 上几乎兑现不了。反过来，任何以性能/二进制体积推 Rust 的论证，在单机 CLI 场景下也都不成立。

14.4 选 Go 必须接受的代价（已写入设计）

  1. keyring 库改选 99designs/keyring（自带文件后端降级——headless/麒麟刚需）；
  2. TOML 不保注释（go-toml v2）→ Codex config.toml 整块重写 + 写前快照兜底，注释免责已写入保真边界；
  3. CGO_ENABLED=0 构建纪律 + CI 静态断言——红利需要纪律锁住；
  4. err 样板多 → errcheck + govet 强制进 CI；
  5. 无编译期穷尽检查 → golden-file 测试集从 P0 就建；
  6. P3 插件化放弃 Go plugin（不支持 Windows），直接用 hashicorp/go-plugin 外置进程方案；
  7. 发布工程预算：macOS 公证、Windows 签名。

16边界与开放问题

16.1 有意的边界（不是遗漏）

  • 企业管理层（managed）只读、远程订阅层（remote）不写回：managed 采集供审计比对、不参与物化（管理权在企业侧）；remote 采集后参与本地合并，但系统不会替你写回组织的远程源。
  • 可执行插件不做跨工具语义翻译：Codex 的 Starlark 执行策略、Cline/Amp 的 TS 插件，IR 保真存储 + 导出时降级警告。翻译代码就是移植程序，超出配置工具的合理边界。
  • 权限/审批模型暂不标准化：Roo 的 groups+fileRegex、Cline 的权限体系等各工具差异过大，当前以扩展位承载，记录为未来的标准化候选。
  • 不做实时双向同步：守护进程式的文件监听留待后续评估，首版是显式的 collect/export。

16.2 待决策的开放问题

  • 项目正式命名：已定名 cfg4ai（2026-08-17，GitHub 零占用验证）；
  • 是否支持 profile 的远程订阅（团队规范下发）；
  • 是否需要 watch 模式（文件变更自动采集）；
  • 真实世界样本库的持续扩充机制（当前以官方示例为主）。

16.3 已知遗留事项

  • Zhanlu 的部分键结构待校准（无公开文档，本机实证仅见 permission 顶级键，适配器需防御式探测）；
  • Claude plugin 键表、Codex subagent TOML 层键表等 3 处字段档案留有核实方法，实现对应适配器前补完；
  • ~/.claude.json 无官方文档，需 P0 实采脱敏后枚举其完整键表。
